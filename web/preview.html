Worth testing

The parts most likely to surprise you, and what "working" looks like.

  • Emergency SOS — traveller app → More → hold the button for three seconds. A short press must cancel. With no contact saved it says so rather than pretending to send. Signed out or offline it opens a text message instead.
  • Claim an offer — traveller app → a listing under “Stops on this corridor” → Claim. The code comes from the server. Claiming twice is refused, because each offer is one per traveller.
  • Colours — control panel → Appearance → pick a palette. The preview in the dialog follows immediately; the traveller app picks it up when its tab regains focus.
  • Bus reviews reach the owner — rate a bus, then open the same bus in the owner portal. The company sees the review and the themes, never who wrote it.
  • Route guides and itineraries — traveller app → Trips. Roads are ordered along the corridor; places are grouped by day. Both are set in the control panel.
  • Offline — load the traveller app, then switch off Wi-Fi and reload. It keeps working on cached content. Emergency numbers are saved on the device on purpose.
Test logins are not in this folder. They live in Bato_Docs/Bato_Test_Accounts.md, kept out of the project and out of GitHub so that real passwords are never published. Staff accounts also ask for an authenticator code.

If something is not running

The launcher starts everything; this is what it starts.

  • Double-click Start_Bato.command in the project folder. It starts the database, applies migrations, loads demo content on first run, then starts both servers.
  • The web app must be served from http://localhost:5173. That is the only address the API accepts by default, so another port cannot reach it. Opening the file directly with file:// will not work either.
  • API logs are at /tmp/bato_backend.log, web server logs at /tmp/bato_web_server.log.
